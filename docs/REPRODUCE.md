# Reproduce the two-Spark deployment

These commands are for Linux on the head Spark unless labeled otherwise. The published helpers were checked offline against the actual deployed source. The existing deployment was verified on hardware; this newly organized guide has not been run as a fresh install on a second pair of Sparks. Keep that distinction when reporting your results.

## 1. Prepare two available nodes and their fabric

Use two Sparks with working NVIDIA container support, Docker access, Git, Python 3, rsync, and enough local NVMe space. We used local replicas, not a worker reading all weights over NFS. Do the large downloads and preparation before serving; the model leaves limited RAM for unrelated work. Inspect the installed driver and container compatibility before upgrading anything.

Establish key-based SSH from head to worker. Verify both management reachability and the **dedicated CX7 fabric**. Our example addresses are `10.42.0.1/24` and `10.42.0.2/24`; substitute your own. They are not the desktop API address unless your desktop can route to that network.

On each node:

```bash
nvidia-smi
docker ps
ip -br -4 addr
rdma link show
```

The selected Ethernet interface must own that node's fabric IPv4 address and its RDMA link must be active. Inspect the GID table for its HCA, replacing the example HCA name:

```bash
HCA=rocep1s0f0
BASE=/sys/class/infiniband/$HCA/ports/1
for f in "$BASE"/gids/*; do
  i=${f##*/}
  printf '%s  %s  %s\n' "$i" "$(cat "$f")" "$(cat "$BASE/gid_attrs/types/$i")"
done
```

Choose the **IPv4-mapped address belonging to the fabric and type `RoCE v2`**. Set `HEAD_GID` and `WORKER_GID` independently. Index 3 is an example, not a universal constant. A populated IPv6 GID at index 3 is not interchangeable with the IPv4 GID on the other node. See [the recovery example](OPERATIONS.md#fabric-address-and-gid-after-a-reboot) for persistent network configuration.

Verify ping and SSH across the fabric before loading the model. The serving kit's preflight cannot substitute for selecting the correct address family.

## 2. Pin the kit and prepare its configuration

```bash
git clone --config core.autocrlf=false https://github.com/ultradaoto/deepseek-v41-exl3-two-sparks.git "$HOME/deepseek-v41-exl3-two-sparks"
git clone --config core.autocrlf=false https://github.com/MiaAI-Lab/DeepSeek-v4.1-Flash-EXL3-2x-DGX-Sparks.git "$HOME/dsv41-kit"
git -C "$HOME/dsv41-kit" checkout 85305680fb0f8ebc72b7b8ebf49ba54471019285
cp "$HOME/dsv41-kit/.env.example" "$HOME/dsv41-kit/.env"
```

Edit that `.env` using [the profile](../examples/profile.env): replace each existing matching value and keep the kit's other defaults. Set your actual username, worker home, addresses, interfaces, and GIDs. Use absolute directories after expansion. `ENGRAM_DIR` is the native source; `ENGRAM_SRC` is the slim source generated by the kit. Keep both independent of compilation-cache paths.

The tested profile uses TP=2, DSpark with three draft tokens, two sequences, a 2,048-token prefill batch, a pinned 1 GiB KV pool, and 131,072 configured context. Do not inherit the upstream example's larger context or KV allocation unintentionally. Do not force an unrelated KV dtype or quantization backend.

The pinned launcher sources `.env` after the caller's environment and only preserves some shell overrides. In particular, keep the hook switches and overlay override **out of `.env`**, and replace the two cache-path assignments there when changing configurations.

## 3. Download the pinned data

In a Python environment with the Hugging Face CLI available:

```bash
python3 -m venv "$HOME/dsv41-tools"
source "$HOME/dsv41-tools/bin/activate"
python -m pip install -r "$HOME/deepseek-v41-exl3-two-sparks/requirements.txt" huggingface_hub
mkdir -p "$HOME/dsv41-data/model" "$HOME/dsv41-data/native-engram"

hf download Mia-AiLab/DeepSeek-V4.1-Flash-EXL3-2.9bpw \
  --revision 64ba41b6c916a587db06eae2e19b7845f7be6e6b \
  --local-dir "$HOME/dsv41-data/model"

hf download deepseek-ai/DeepSeek-V4.1-Flash \
  model-00047-of-00048.safetensors model-00048-of-00048.safetensors \
  model.safetensors.index.json config.json LICENSE \
  --revision dba1be0a40aa45a94ad051997016db3960a90277 \
  --local-dir "$HOME/dsv41-data/native-engram"
```

Expect 39 EXL3 shards (196.14 GiB) plus the two native Engram shards (189.13 GiB). The native index **and native `config.json`** are needed. Missing `/engram-src/config.json` caused an earlier failure in this deployment; the pinned kit's slim-source helper copies it only when it exists in the source directory. Do not place native Engram shards into the EXL3 checkpoint tree. `WEIGHT_SYNC=rsync` copies the required model and slim Engram tree to the worker during the first launcher run; allow time and disk space for that copy. The helper hard-links native shards into the slim source on the same filesystem; different filesystems may require an extra physical copy on the head.

`AUTO_DOWNLOAD=0` makes the launcher verify these staged files instead of silently fetching a moving upstream revision. Check download completion before continuing.

## 4. Establish a stock baseline

Pull the immutable image and give it a local tag for reliable image shipping. Substitute your worker SSH destination:

```bash
BASE_IMAGE=ghcr.io/miaai-lab/deepseek-v4.1-flash-exl3-2x-dgx-sparks@sha256:2f0cf3adc0f989c1d446be274df864eb799630175f604c3b22b71b7205971dce
WORKER_SSH=sparkuser@10.42.0.2
docker pull "$BASE_IMAGE"
docker tag "$BASE_IMAGE" dsv41-flash-exl3:stock-pinned
set -o pipefail
docker save dsv41-flash-exl3:stock-pinned | ssh "$WORKER_SSH" docker load

cd "$HOME/dsv41-kit"
SKIP_PULL=1 SKIP_BUILD=1 SKIP_SHIP=1 TAIL=0 ./start.sh
```

At this stage `.env` must still select `dsv41-flash-exl3:stock-pinned`, and the hook must be unset. Do **not** set `SKIP_SYNC=1` on the first run. The launcher creates the slim Engram source and copies files to the worker. Compare the local image IDs on both nodes after shipping.

When startup finishes, test generation:

```bash
python "$HOME/deepseek-v41-exl3-two-sparks/tools/check_api.py"
```

Expected: `323`, `passed: true`. HTTP `/health` or an accepted streaming connection alone does not prove that both tensor-parallel ranks can generate.

## 5. Obtain and derive the small parameter file

On a separate CPU machine, or while the Sparks are stopped, obtain access to [the original overlay repository](https://huggingface.co/drowzeys/DeepSeek-V4.1-Flash-Abliterated-Cybersecurity-Unleashed) and accept its agreement using your own account. Then:

```bash
hf auth login
hf download drowzeys/DeepSeek-V4.1-Flash-Abliterated-Cybersecurity-Unleashed \
  wo_b_l10_35.safetensors \
  --revision 87bb9850e6f49fd20ad9c8516b7817215cbbf5fc \
  --local-dir ./downloads

python tools/derive_params.py \
  --overlay ./downloads/wo_b_l10_35.safetensors \
  --out ./build/params/wob_hook_params.npz
```

Run the Python command from this guide repository. Its NumPy dependency is in `requirements.txt`. This downloads approximately another gigabyte of selected native FP8 tensor byte ranges, rather than the full native backbone. It checks range responses and does not bypass gated access. Give the CPU calculation time; each of 26 matrices has over 41 million elements.

Use **`wo_b_l10_35.safetensors`**, the original FP8 artifact, for derivation. The newer `mia_exl3_wo_b_l10_35.safetensors` is a pre-encoded weight-graft alternative and cannot be decoded by this script.

The script sign-aligns and averages the dominant directions and writes `r`, layers 10–35, and 26 alpha values of 3.5. It also writes a derivation report. The original full-matrix fit was approximately 3.35; subsequent quantizer analysis supported 3.5 as the intended strength. See [design rationale](DESIGN.md). Numerical-library differences and quantization bias mean regeneration is not promised to reproduce the tested artifact byte for byte.

Transfer your resulting NPZ to the head. The tested NPZ was 21,534 bytes with SHA-256 `abf42531f925f418aa1914cdf50c51db474ec62b296b8de18ea1cfb8ac335a60`. An independently derived file is a new artifact and needs its own checks.

## 6. Prepare and build the runtime hook

On the head, after choosing the NPZ location:

```bash
GUIDE="$HOME/deepseek-v41-exl3-two-sparks"
KIT="$HOME/dsv41-kit"
BUILD_DIR="$HOME/dsv41-hook-build"
python "$GUIDE/tools/prepare.py" \
  --kit "$KIT" --params /absolute/path/to/wob_hook_params.npz --out "$BUILD_DIR"
bash -n "$KIT/start.sh"
docker build -t dsv41-flash-exl3:rank1-hook "$BUILD_DIR"
set -o pipefail
docker save dsv41-flash-exl3:rank1-hook | ssh "$WORKER_SSH" docker load
```

The helper requires the pinned stock overlay/launcher hashes, validates the NPZ, appends the exact deployed runtime code, and adds the three environment variables to **both** ranks' launcher paths. It backs up `start.sh` as `start.sh.before-runtime-hook`. Generated overlay and launcher hashes must exactly match the deployed versions recorded in its manifest. It does not rewrite weights or launch a model. Use LF checkouts: Windows CRLF conversion changes these hashes and is intentionally rejected rather than silently accepted.

The small derived image inherits the pinned image's compiled runtime. It adds `/opt/dsv41/exl3.py` and `/opt/dsv41/wob_hook_params.npz`. The launcher **bind-mounts its chosen host overlay over the baked overlay**, so setting `EXL3_OVERLAY_HOST` at launch is essential.

## 7. Switch at a process boundary and verify

Finish active requests first. Stop the pair with the existing launcher; do not reboot the machines:

```bash
cd "$KIT"
./start.sh stop
```

Read `config_id` from `$BUILD_DIR/manifest.json`. Edit `.env` so `CACHE_ROOT` and `WORKER_VLLM_CACHE` point to **new, unused directories** containing that ID and a run suffix, for example `.../dsv41-hook-<config_id>-run1`. Keep `ENGRAM_SRC`, `HEAD_ENGRAM_BIND`, and `WORKER_ENGRAM_BIND` at their existing independent data paths. Changing the direction, alpha, layer set, or hook code requires a new configuration/cache boundary.

```bash
EXL3_OVERLAY_HOST="$BUILD_DIR/exl3.py" \
ABLIT=1 ABLIT_ALPHA=3.5 ABLIT_PARAMS=/opt/dsv41/wob_hook_params.npz \
IMAGE=dsv41-flash-exl3:rank1-hook \
SKIP_PULL=1 SKIP_BUILD=1 SKIP_SHIP=1 SKIP_SYNC=1 TAIL=0 ./start.sh
```

`SKIP_SYNC=1` is appropriate only after the stock run established both replicas. There is no need to recopy unchanged weights. Confirm the image ID and the mounted overlay hash on both nodes, and then inspect logs **since the current start**:

```bash
STARTED=$(docker inspect -f '{{.State.StartedAt}}' dsv41-exl3-head)
docker logs --since "$STARTED" dsv41-exl3-head 2>&1 | grep '\[ablit\]'
python "$GUIDE/tools/check_api.py"
```

Repeat the log inspection on the worker using `dsv41-exl3-worker`. Require 26 unique fired layers, 10–35, alpha `3.500`, on each rank. The installation message alone is insufficient. Then run several benign coherence prompts and a fixed, authorized evaluation set against your saved stock baseline. Compare complete responses; treat token-limit completions as inconclusive.

The historical alpha-100 liveness experiment deliberately produced incoherent text on a disposable serve. It is evidence that the hook path was active, **not a recommended routine production test**. The normal reproduction checks use alpha 3.5.

Now [connect Goose](GOOSE.md). Preserve your manifests and measurements; the published A/B counts apply to the original tested parameter file, not automatically to your regenerated file.
